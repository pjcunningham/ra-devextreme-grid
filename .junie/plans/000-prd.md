# ra-devextreme-grid

## Product Requirements Document

**Repository:** `https://github.com/pjcunningham/ra-devextreme-grid`
**Status:** Initial PRD
**Project type:** Open-source React/TypeScript library
**Primary package:** `ra-devextreme-grid`
**Target ecosystem:** React-Admin + DevExpress DevExtreme React DataGrid
**Backend reference implementation:** FastAPI + SQLModel
**Python tooling:** UV
**Frontend package manager:** pnpm

---

# 1. Executive Summary

`ra-devextreme-grid` will provide a reusable integration between React-Admin and the DevExpress DevExtreme React DataGrid.

The primary motivation is to allow React-Admin applications to use DevExtreme DataGrid as an alternative to React-Admin's built-in grid components and its AG Grid Enterprise integration.

The project should preserve the parts of React-Admin that it handles well:

* resource management;
* routing;
* authentication;
* authorization;
* data providers;
* mutations;
* notifications;
* forms;
* record contexts;
* list actions;
* bulk actions;
* application structure.

DevExtreme DataGrid should be responsible for grid-specific behaviour such as:

* column management;
* sorting;
* filtering;
* paging;
* selection;
* scrolling;
* grouping;
* summaries;
* state persistence;
* remote data processing;
* grid interaction.

The project will support two distinct integration modes.

1. **React-Admin managed mode**

   React-Admin fetches list data through its normal `getList()` mechanism and DevExtreme renders and interacts with that data.

2. **DevExtreme remote mode**

   DevExtreme controls paging, filtering, sorting, grouping and summaries using `CustomStore` and `remoteOperations`. Requests are passed through an extended React-Admin `dataProvider`.

The second mode is particularly important for large datasets and server-driven applications.

The project should not attempt to replace React-Admin. It should replace or supplement its grid layer.

---

# 2. Problem Statement

React-Admin provides capable list components and React-Admin Enterprise provides an AG Grid integration.

However, applications may already standardise on DevExpress DevExtreme and may prefer its licensing, deployment model, API, or server-side data capabilities.

There is currently no first-class reusable adapter that makes DevExtreme DataGrid behave like a natural React-Admin grid.

Simply placing a DevExtreme DataGrid inside a React-Admin page is insufficient because important React-Admin concepts would be lost or duplicated, including:

* current resource;
* record identifiers;
* list state;
* row selection;
* bulk actions;
* navigation;
* data provider access;
* mutations;
* notifications;
* permissions;
* loading/error state.

The project therefore needs an explicit integration layer.

---

# 3. Product Vision

A React-Admin developer should be able to replace a conventional list grid with DevExtreme using a small amount of code while preserving normal React-Admin application behaviour.

A simple list should eventually look approximately like:

```tsx
const CustomerList = () => (
    <List>
        <DatagridDX>
            <DxColumn dataField="id" width={90} />
            <DxColumn dataField="companyName" caption="Company" />
            <DxColumn dataField="contactName" caption="Contact" />
            <DxColumn dataField="active" dataType="boolean" />
        </DatagridDX>
    </List>
);
```

For large datasets, a developer should be able to use a remote grid:

```tsx
const CustomerList = () => (
    <DatagridDXRemote
        columns={[
            { dataField: "id", width: 90 },
            { dataField: "companyName", caption: "Company" },
            { dataField: "contactName", caption: "Contact" },
            { dataField: "active", dataType: "boolean" },
        ]}
    />
);
```

The remote grid should obtain the current resource from React-Admin and use the application's `dataProvider`.

# 4. Goals

The project SHALL:

1. Provide a reusable React component for rendering React-Admin list data using DevExtreme DataGrid.

2. Preserve React-Admin resource context and navigation conventions.

3. Integrate React-Admin row selection with DevExtreme selection.

4. Support React-Admin edit/show navigation from grid rows.

5. Support the existing React-Admin `dataProvider` contract wherever the standard contract is sufficient.

6. Define a small, typed extension to the React-Admin `dataProvider` for DevExtreme remote operations.

7. Support DevExtreme remote paging.

8. Support DevExtreme remote filtering.

9. Support DevExtreme remote multi-column sorting.

10. Support remote grouping and summaries in later phases before the stable 1.0 release.

11. Provide strong TypeScript typings.

12. Allow applications to access the underlying DevExtreme DataGrid functionality without the adapter artificially restricting it.

13. Remain independent of any particular HTTP API design.

14. Include a FastAPI reference implementation demonstrating server-side processing.

15. Use SQLModel for the reference application's database models and normal data access where practical.

16. Use SQLAlchemy expressions underneath SQLModel where required for dynamic query construction.

17. Be suitable for open-source publication and eventual npm publication.

18. Use only public React-Admin APIs.

19. Work with standard open-source React-Admin and not require React-Admin Enterprise.

20. Be compatible with React-Admin Enterprise applications.

---

# 5. Non-Goals

The initial project SHALL NOT:

* replace React-Admin itself;
* provide an alternative authentication system;
* provide an alternative authorization system;
* replace React-Admin forms;
* duplicate DevExtreme DataGrid features unnecessarily;
* reproduce every feature of `DatagridAG`;
* support arbitrary SQL expressions supplied by clients;
* allow clients to query arbitrary database columns;
* require FastAPI;
* require SQLModel in consuming applications;
* require Python in consuming applications;
* provide an ORM-independent Python query framework in the first release;
* support DevExtreme TreeList;
* support DevExtreme PivotGrid;
* implement offline synchronisation;
* implement realtime updates in the initial release;
* implement arbitrary client-provided executable expressions.

The backend example is a reference implementation, not a mandatory server component.

# 6. Design Principles

## 6.1 React-Admin remains the application framework

React-Admin continues to own application-level concerns.

DevExtreme owns grid-level concerns.

The integration should not create a parallel admin framework.

## 6.2 Prefer composition over reimplementation

Where DevExtreme already implements a capability well, the adapter should expose or configure that capability rather than reimplementing it.

## 6.3 Use React-Admin public APIs only

The adapter must not depend on undocumented React-Admin internals.

This reduces upgrade risk.

## 6.4 Keep remote mode explicitly different from standard list mode

React-Admin's normal list state supports concepts such as:

```text
page
perPage
sort
filter
selectedIds
```

DevExtreme remote processing can represent richer state including:

```text
skip
take
multiple sort expressions
nested filters
groups
group summaries
total summaries
group counts
```

The project must not distort or discard DevExtreme's remote query model merely to force it through React-Admin's standard `getList()` interface.

## 6.5 Backend agnostic core

The TypeScript package must not assume FastAPI, SQLModel, REST, GraphQL, or any specific URL structure.

Transport belongs to the consuming application's `dataProvider`.

## 6.6 Secure by default

Server-side field names and operations must be explicitly whitelisted.

Never concatenate untrusted column names or expressions directly into SQL.

## 6.7 Escape hatches are important

Advanced DevExtreme users must be able to access native DataGrid properties and events where doing so does not conflict with adapter-controlled behaviour.

# 7. Target Users

The primary user is a developer who:

* already uses React-Admin;
* wants DevExtreme DataGrid for list views;
* may already have a DevExtreme licence;
* has medium or large datasets;
* wants strong server-side processing;
* does not want to replace React-Admin's CRUD application framework.

A secondary user is a developer building conventional smaller React-Admin applications who simply prefers DevExtreme's grid UI.

# 9. Integration Modes

## 9.1 Mode A — React-Admin Managed Grid

Component working name:

```tsx
<DatagridDX />
```

This component SHALL normally be rendered inside a React-Admin `<List>`.

Example:

```tsx
const ProductList = () => (
    <List>
        <DatagridDX>
            <DxColumn dataField="id" />
            <DxColumn dataField="name" />
            <DxColumn dataField="price" dataType="number" />
        </DatagridDX>
    </List>
);
```

`DatagridDX` SHALL consume React-Admin's `ListContext`.

React-Admin remains responsible for fetching.

The component must not independently execute a second `getList()` request.

Initial state mappings include:

```text
React-Admin                 DevExtreme

data                    ->  dataSource
isPending/isFetching    ->  loading indication
selectedIds             <-> selectedRowKeys
onSelect                <-  selection changes
page/perPage            <-> paging
sort                    <-> supported single-column sort state
```

This mode prioritises compatibility with standard React-Admin list behaviour.

### Limitation

React-Admin's normal list sort model does not fully represent DevExtreme multi-column remote sorting.

Features that cannot be represented faithfully through `ListContext` SHALL either:

* operate client-side where appropriate;
* be disabled;
* or require remote mode.

The adapter must document such limitations explicitly.

---

# 10. Mode B — DevExtreme Remote Grid

Component working name:

```tsx
<DatagridDXRemote />
```

Remote mode SHALL be resource-aware but SHALL NOT require React-Admin `<List>` to fetch its records.

It should use:

```tsx
useResourceContext()
useDataProvider()
```

and other public React-Admin hooks as appropriate.

DevExtreme `CustomStore` SHALL control data loading.

The remote grid SHALL support, progressively:

```text
skip
take
requireTotalCount
sort
filter
group
requireGroupCount
totalSummary
groupSummary
```

The complete feature set will be delivered incrementally.

Remote mode SHALL use DevExtreme's `remoteOperations`.

No duplicate React-Admin `getList()` request should occur.

---

# 11. React-Admin DataProvider Extension

The remote adapter will define a typed React-Admin data provider extension.

Working interface:

```ts
export interface DevExtremeDataProvider extends DataProvider {
    getGrid<RecordType extends RaRecord = RaRecord>(
        resource: string,
        params: GetGridParams,
    ): Promise<GetGridResult<RecordType>>;
}
```

Initial request shape:

```ts
export interface GetGridParams {
    loadOptions: SerializableGridLoadOptions;
    meta?: Record<string, unknown>;
    signal?: AbortSignal;
}
```

The serialisable load options should represent the supported DevExtreme query subset.

Conceptually:

```ts
export interface SerializableGridLoadOptions {
    skip?: number;
    take?: number;

    requireTotalCount?: boolean;
    requireGroupCount?: boolean;

    sort?: GridSort[];
    filter?: GridFilter;

    group?: GridGroup[];

    totalSummary?: GridSummary[];
    groupSummary?: GridSummary[];
}
```

Result:

```ts
export interface GetGridResult<RecordType> {
    data: RecordType[] | GridGroupResult[];

    totalCount?: number;
    groupCount?: number;

    summary?: unknown[];
}
```

The exact TypeScript types SHALL be researched against the current DevExtreme version during implementation.

The public API should avoid unnecessarily duplicating DevExtreme's own types where those types are stable and appropriate.

However, only JSON-serialisable query data may be sent to a backend.

Functions or executable selectors must never be serialised for remote execution.

# 12. Why `getGrid()` Exists

React-Admin's standard:

```ts
getList()
```

is ideal for ordinary React-Admin lists.

It is not sufficiently expressive for all DevExtreme server operations.

For example, DevExtreme can request:

```ts
sort: [
    { selector: "surname", desc: false },
    { selector: "createdAt", desc: true },
]
```

and nested filters such as:

```ts
[
    ["active", "=", true],
    "and",
    [
        ["name", "contains", "smith"],
        "or",
        ["company", "contains", "smith"],
    ],
]
```

It can additionally request grouping and aggregate summaries.

The custom method therefore preserves the native server query semantics.

`getGrid()` remains an application-level transport abstraction.

The npm package must not dictate that `getGrid()` uses REST or a particular endpoint.

# 13. Reference FastAPI Transport

The repository SHALL eventually contain a reference backend.

Example endpoint:

```text
POST /api/customers/grid
```

Example request:

```json
{
    "skip": 0,
    "take": 50,
    "requireTotalCount": true,
    "sort": [
        {
            "selector": "company_name",
            "desc": false
        }
    ],
    "filter": [
        ["active", "=", true],
        "and",
        ["company_name", "contains", "smith"]
    ]
}
```

Example response:

```json
{
    "data": [],
    "totalCount": 378
}
```

Later:

```json
{
    "data": [],
    "totalCount": 378,
    "groupCount": 12,
    "summary": [
        127650.50
    ]
}
```

POST is preferred in the reference application because complex filter/group definitions can become awkward or excessively long as query-string parameters.

This choice is not imposed on users of the npm package.

# 15. Server-Side Field Registry

The backend MUST NOT allow arbitrary model attributes supplied by the browser.

Each resource SHALL define the fields available to grid queries.

Conceptual example:

```python
customer_grid = GridDefinition(
    fields={
        "id": Customer.id,
        "company_name": Customer.company_name,
        "contact_name": Customer.contact_name,
        "active": Customer.active,
        "created_at": Customer.created_at,
    }
)
```

The server must resolve selectors exclusively through this registry.

A request for:

```text
password_hash
```

or any unknown selector must fail safely.

Fields may later carry capability metadata:

```python
GridField(
    expression=Customer.company_name,
    sortable=True,
    filterable=True,
    groupable=True,
    summarizable=False,
)
```

# 16. Supported Filtering

Filtering will be implemented incrementally.

Initial operators SHOULD include:

```text
=
<>
>
>=
<
<=
contains
notcontains
startswith
endswith
```

Logical operations SHOULD include:

```text
and
or
!
```

The compiler must support nested expressions.

Example:

```text
(A AND B) OR (C AND (D OR E))
```

Tests for nested filtering are mandatory.

Special care is required for:

* strings;
* integers;
* decimals;
* booleans;
* dates;
* datetimes;
* nullable fields;
* enums.

Filtering behaviour must be deterministic and documented.

---

# 17. Sorting

Standard React-Admin mode initially supports React-Admin's normal single sort state.

Remote mode SHALL support DevExtreme multi-column sorting.

Example:

```json
[
    {
        "selector": "surname",
        "desc": false
    },
    {
        "selector": "created_at",
        "desc": true
    }
]
```

The backend must apply sorts only against registered fields.

Stable ordering should be considered when pagination is active.

Where required, a deterministic key such as `id` may be appended internally as a tie-breaker.

---

# 18. Paging

Remote mode SHALL initially support:

```text
skip
take
requireTotalCount
```

Server responses must calculate `totalCount` after filtering but before applying `skip` and `take`.

Maximum page sizes should be configurable server-side.

A malicious or accidental request for an excessively large `take` value must not force an unlimited database result.

---

# 19. Grouping and Summaries

Grouping is an important long-term capability and should be included before declaring the remote integration feature-complete.

The project should progressively support:

```text
group
requireGroupCount
groupSummary
totalSummary
```

Initial summary operations SHOULD include:

```text
count
sum
min
max
avg
```

Group paging should be treated as a separate advanced phase because it changes server query semantics substantially.

Grouping and summaries must not be added until paging, sorting and filtering are thoroughly tested.

---

# 20. Columns

The initial adapter SHOULD use DevExtreme-native column definitions.

For example:

```tsx
<DatagridDX>
    <DxColumn
        dataField="companyName"
        caption="Company"
    />
</DatagridDX>
```

or:

```tsx
<DatagridDX
    columns={[
        {
            dataField: "companyName",
            caption: "Company",
        },
    ]}
/>
```

The implementation should determine whether both forms can be supported cleanly.

The adapter should not invent a new column DSL unless necessary.

Support for React-Admin field components such as:

```tsx
<TextField />
<DateField />
<ReferenceField />
```

inside DevExtreme cells is desirable but not required for the first MVP.

A later implementation may provide a cell renderer that supplies:

```tsx

    ...
</RecordContextProvider>
```

This capability must be implemented only after the native DevExtreme column path is stable.

# 22. Row Navigation

The grid SHALL eventually support React-Admin-style row navigation.

Proposed API:

```tsx
<DatagridDX rowClick="edit" />
```

Supported values should include:

```ts
"edit"
"show"
false
```

A callback form may later be supported.

Navigation must use React-Admin routing APIs rather than constructing URLs manually where an appropriate public API exists.

---

# 23. Row Selection

In React-Admin managed mode:

```text
DevExtreme selectedRowKeys
        ↕
React-Admin selectedIds
```

Selection must remain synchronised.

This allows React-Admin bulk actions to continue operating.

The adapter must prevent feedback loops where updating one selection model repeatedly triggers the other.

Selection of identifiers must support React-Admin `Identifier` types rather than assuming numeric IDs.

---

# 24. Bulk Actions

React-Admin bulk actions should work in managed mode once row selection is integrated.

Remote mode presents a harder problem because standard React-Admin list components expect `ListContext`.

Remote bulk-action compatibility should therefore be implemented incrementally.

The adapter should not construct a fake or incomplete `ListContext` simply to satisfy component types.

If a compatible `ListContext` is provided in remote mode, it must contain coherent state and behaviour.

---

# 25. Editing

Inline editing is useful but is NOT part of the first read-only MVP.

Later versions should support:

```text
row editing
cell editing
create
update
delete
```

Where practical, mutations should travel through React-Admin's mutation APIs rather than bypassing React Query and React-Admin cache behaviour.

Editing must address:

* optimistic vs pessimistic updates;
* server validation errors;
* refresh behaviour;
* React Query cache invalidation;
* DevExtreme data source refresh;
* notifications;
* authentication errors.

Editing should therefore be implemented only after remote reading is stable.

---

# 26. Loading and Error Handling

The adapter SHALL provide coherent states for:

* initial loading;
* background refresh;
* empty dataset;
* request failure;
* mutation failure.

React-Admin authentication/error behaviour should not be bypassed unnecessarily.

Error messages should remain accessible to application code.

The library should not silently swallow exceptions.

---

# 27. Grid State Persistence

DevExtreme supports persistence of grid configuration.

The project should eventually support persistence of:

* column order;
* column width;
* visibility;
* filtering state;
* sorting state;
* paging state where appropriate.

The adapter should investigate integration with React-Admin's preference/store APIs.

The first implementation may use DevExtreme's native state-storage mechanisms.

The package must not impose browser `localStorage` if the consuming application wants another persistence mechanism.

---

# 28. Native DevExtreme Props

Users SHALL have access to normal DevExtreme DataGrid configuration.

The adapter should expose native DataGrid properties wherever possible.

Adapter-owned props must be clearly documented.

Potential conflicting props should either:

* be omitted from the exposed native type;
* be overridden intentionally;
* or have clearly defined precedence.

Avoid wrapping DevExtreme so aggressively that advanced DevExtreme functionality becomes inaccessible.

---

# 29. Styling and Themes

The library SHALL NOT force a specific DevExtreme visual theme.

The consuming application is responsible for importing its desired DevExtreme stylesheet.

Documentation and examples may use a standard DevExtreme theme.

The package should avoid unnecessary global CSS.

Any adapter-specific CSS should be minimal.

# 36. Testing Strategy

Testing is a first-class requirement.

Every phase must add or update tests appropriate to the implemented behaviour.

## TypeScript unit tests

Unit tests should cover pure mapping and state logic, including:

* React-Admin state to DevExtreme state;
* DevExtreme events to React-Admin callbacks;
* selection synchronisation;
* query normalisation;
* result conversion;
* remote load options;
* invalid options.

## React component tests

React Testing Library should verify:

* rendering;
* loading;
* empty data;
* row selection;
* navigation callbacks;
* relevant context integration.

## Browser tests

Playwright should be introduced where behaviours cannot be tested confidently without an actual DataGrid/browser environment.

Likely candidates include:

* paging;
* sorting;
* filtering;
* selection;
* persistent state;
* remote request generation.

## Python tests

The FastAPI backend must have substantial unit coverage around:

* field whitelisting;
* filter parsing;
* nested expressions;
* sorting;
* paging;
* count queries;
* grouping;
* summaries;
* invalid requests;
* malicious selectors;
* data types.

The SQL query translation layer requires particularly strong tests.

# 46. Performance Expectations

Managed mode should not introduce unnecessary rendering or duplicate fetching.

Remote mode must allow the server to process large datasets without transferring the complete dataset to the browser.

No fixed record-count promise is required.

The architecture must nevertheless be suitable for datasets large enough that client-side loading is impractical.

Backend queries should:

* apply filters in the database;
* apply sorting in the database;
* perform paging in the database;
* calculate counts efficiently;
* perform supported aggregates in the database.

Python code must not load the complete table into memory merely to reproduce grid operations.

---

# 47. Security Requirements

The project must treat all remote grid requests as untrusted input.

The reference backend SHALL:

* validate request structure;
* whitelist fields;
* whitelist operators;
* reject unknown selectors;
* reject unsupported operators;
* cap page sizes;
* avoid dynamic Python evaluation;
* avoid `eval`;
* avoid arbitrary SQL fragments;
* use SQLAlchemy expression objects;
* avoid SQL string concatenation based on client input.

Tests should intentionally attempt invalid and hostile-looking selectors and expressions.

# 48. Compatibility Strategy

Compatibility should be tested, not assumed.

The project should initially target current stable versions at project bootstrap.

The README must document the versions actually tested.

React-Admin and DevExtreme upgrades should be performed deliberately.

CI may later use a compatibility matrix once the library has users and a stable release.

The core package should avoid hard dependencies on React-Admin Enterprise so that the adapter remains useful to the wider React-Admin community.

# 51. Initial Architectural Decisions

The following decisions are accepted unless implementation evidence provides a strong reason to revisit them.

### Decision A

The repository will provide a React-Admin integration, not a generic DevExtreme wrapper.

### Decision B

Managed mode and true DevExtreme remote mode are different architectural concerns and will be treated separately.

### Decision C

React-Admin's standard `getList()` will be used when it adequately represents the operation.

### Decision D

A custom `getGrid()` data-provider method will be used for richer DevExtreme remote queries.

### Decision E

The TypeScript adapter will remain backend agnostic.

### Decision F

FastAPI + SQLModel will be the project's reference backend.

### Decision G

Dynamic SQL operations will use safe SQLAlchemy expression construction.

### Decision H

The Python reference implementation will remain inside the example application initially rather than becoming a premature separately published library.

### Decision I

DevExtreme-native columns are the primary column API for the MVP.

### Decision J

React-Admin field-component rendering is a later enhancement.

### Decision K

Inline editing will follow stable read-only remote support rather than being implemented immediately.

### Decision L

The package will rely only on supported public React-Admin APIs.

# 52. Success Criteria

The project is successful when a React-Admin developer can install `ra-devextreme-grid`, configure DevExtreme, and obtain a grid that feels native to both libraries rather than like one framework has merely been embedded inside the other.

The strongest success case is a React-Admin application backed by a large database where DevExtreme can send rich server-side grid operations through the React-Admin data-provider boundary and a backend can execute those operations safely and efficiently without loading the full dataset into the browser.
